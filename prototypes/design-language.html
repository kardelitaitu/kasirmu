Design Language

Color Palette

Core tokens for backgrounds, text, borders, and semantic states. All values are defined as CSS custom properties for easy theming.

Logic & Strategy

Why 8 colors? The brand palette is deliberately small and borrowed from the iOS system palette — high-chroma hues that stay legible on POS screens viewed from arm's length, in bright kitchens or dim back rooms. Fewer colors means fewer wrong choices, so screens stay consistent.

Why is blue the primary? Blue is the one color users already read as "tappable / interactive" (the web-link convention), and it holds AA contrast on both white and dark surfaces. Keep it reserved for actions — a blue element is always a promise that clicking does something.

Three layers. Brand colors (the raw palette) → semantic roles (what a color means) → neutral scaffolding (surfaces, text, borders). Components use semantic tokens only — never raw brand hex. A rebrand then touches one :root block, not every component.

When to use each role — these are the only allowed meanings:

Primary — interact

Every action the user can take: buttons, links, selected tabs, toggles-on, active filters.

Success — confirm

Completed work: saved, synced, connected. Always paired with a checkmark icon (never green alone).

Danger — destroy

Destructive actions and hard errors: delete, disconnect, fail. One step from a confirm dialog.

Warning — near a limit

Thresholds approaching: order age crossing the yellow line, low paper, nearly full storage.

Info — notify

System messages that need no action: printer connected, sync started, background events.

Alert — act now

Something needs attention immediately — order overdue past the red line. Maps to pink, distinct from danger red.

Accent — decorate

Non-interactive highlights: badges, marketing, decorative fills. Never used for actions or status.

Mapping rule: a semantic role may be re-pointed at a different brand colour in dark mode — but the meaning of the role never changes. Always reference the token, never the brand hex.

Fallback & Accessibility

1

Never colour alone

Every status also carries an icon, shape, or text — this is Feedback Rule 05/06. A red border without a message, or green without a checkmark, reads as decoration to anyone who can't see the hue.

2

Red/green is the common colour-blind pair

Never make success vs. danger the only difference between two states. Add the icon; when in doubt, also change the shape or position.

3

Know the weak pairings

--text-muted on white ≈ 3:1 (large/bold text only). White text on --success is low contrast — which is exactly why success always gets the checkmark icon too. Verify any new token pair with a contrast checker before shipping.

4

Tokens, never hex

Components reference var(--token) only. Hardcoded hex breaks dark mode, theming, and future rebrands. If a token is missing, the component inherits the previous value instead of inventing a colour.

5

If the stylesheet fails

The page degrades to browser defaults — black text on white. Content stays readable because no meaning lives in colour alone (rule 1).

Buttons

Complete button system — sizes, variants, icon combos, and interactive states.

Logic & Strategy

Why three sizes? Size is hierarchy, and hierarchy must be obvious at a glance. Large (48px) is the minimum comfortable touch target and marks the one action a screen is about. Medium (42px) is the default for any inline action. Small (34px) is for dense rows, toolbars, and confirm dialogs — never the primary action.

Why so many variants? They form an emphasis ladder — how loudly a button asks for attention: primary (loudest, the main action) → secondary (the alternative) → ghost (quiet, row-level actions) → danger / success (meaning, not volume) → chip (selectable options, not actions).

One primary per view. A screen gets exactly one btn--primary; everything else drops down the ladder. Two primaries compete and neither wins.

Sizes — Large / Medium / Small

Large is for the screen's primary CTA and full-width actions. Medium is the default — use it unless there's a reason not to. Small is for compact rows and dialogs; if a view's only action is small, it should probably be medium.

Semantic Variants

The emphasis ladder in practice: one primary per view; secondary for the escape-hatch action; ghost for row-level edits; danger only for destructive work (delete, disconnect, cancel-forever); success only as a settled confirmation (Saved ✓), never as the resting state of a CTA.

Fallback & Accessibility

1

48px minimum hit target

The large size is the floor for anything a finger might tap. Small (34px) is only for mouse/toolbar contexts — never for the key action on a screen.

2

One primary per view

Exactly one btn--primary. If two actions feel equally primary, the design has a hierarchy problem — resolve it before adding a second primary.

3

Meaning is never colour alone

Danger vs. success is red vs. green — the classic colour-blind pair. Pair every variant with its icon (trash for delete, check for success) and a clear label.

4

Icon-only is never unnamed

Every icon-only button carries an aria-label. No exceptions — a silent round button is a mystery to screen-reader users.

5

Busy buttons must not double-fire

While an action is in flight, disable the button and show feedback (see the Feedback tab's Busy → Done). Otherwise a double-tap triggers the action twice.

Typography

Type scale, weights, and usage guidelines for the design system.

Logic & Strategy

Why Inter? A tall x-height keeps glyphs legible at 14px and below — exactly the sizes a POS screen runs at. It's also a variable font: one ~95KB WOFF2 carries every weight from 400 to 800, so bold never "fakes" itself from a single file.

Why JetBrains Mono? Monospace is for data that must align and compare: code, hex values, IPs, receipt totals. Fixed-width digits make columns line up; the fallback chain keeps it available on every platform.

Strategy. The scale is a strict ladder — 32/24/20/16/14/12/11 — climb it one rung at a time, never skip. Weight follows role: 800 for Display only, 700 for headings and buttons, 600 for subheads, 400 for body. Letter-spacing tightens as size grows (−0.03em at 32px, down to 0 at body size).

Fallback & Accessibility

1

Cap line length

Body text stays within 65–75 characters per line (~45rem). Longer lines are tiring to read and easy to lose your place in — order cards and dialogs follow this too.

2

Truncate, don't wrap, in controls

Buttons and pills use white-space: nowrap + ellipsis. A button label that wraps to two lines breaks the hit-target shape.

3

Screen-reader-only text

When the visual label is an icon or a truncated string, add a visually-hidden span (the sr-only pattern) so assistive tech reads the full text. Same spirit as the Audit tab's aria-label rule.

4

Scale with user settings

Map the scale to rem tokens in production so text scales with the root font size and respects browser zoom / accessibility settings. The px values on this page are the design reference, not literal production CSS.

5

Never fake a weight

Inter is variable, so 400–800 all exist. Where a platform can't load a weight it synthesises one — that's why smoothing is pinned on body (see Anti-Aliasing above): it keeps synthesised weights from looking muddy.

Spacing & Layout

Consistent spacing scale, border radii, and elevation tokens.

Logic & Strategy

Why a 4px base? Every value on the scale is a multiple of 4 — the tightest grid that still divides evenly into 8 and 12. It gives enough granularity for dense POS screens without pixel-fiddling, and because everything is a multiple of 4, components slot together with no magic numbers.

Gap and padding, never margins. Layout spacing comes from gap on flex/grid containers and padding on surfaces. Margins on shared components leak into every context that embeds them; gap and padding belong to the container and stay predictable.

Strategy by size. 4 — micro gaps (icon-to-text, dot-to-label). 8 — the default gap between related controls. 12 — gap between groups. 16 — card padding. 24 — separation between sections. 32+ — page-level rhythm. Use rem for padding that should scale with the user's font size, px for hairline borders.

Shadow SM
Shadow MD

Elevation ladder: --shadow-sm — resting cards and rows on the page. --shadow-md — floating layers: modals, dropdowns, tooltips. --shadow-lg — full-screen overlays and command palettes (rare). Shadow is a closeness signal: more shadow = closer to the user's eye. If you need a fourth level, the layout is the problem, not the token.

Dark-mode fallback: shadows barely read on dark backgrounds — the tint is nearly invisible. In dark mode, elevation is carried by surface tone (lighter surface) + a hairline border instead. Keep shadows in code, but don't rely on them for separation in dark themes.

Fallback & Accessibility

1

No margins for layout

Spacing between elements comes from gap or container padding — never from margins on shared components. Margins make an element impossible to embed safely.

2

8px minimum between touch targets

Adjacent buttons and tappable rows keep at least 8px between hit areas — below that, mis-taps climb sharply on a POS used at speed.

3

Three elevation levels max

Page → card → modal. More levels blur what's actually on top. If something needs to float above a modal, restructure instead.

4

Dark mode: tone + border, not shadow

On dark surfaces shadows are invisible — elevate with a lighter surface fill and a hairline border. Test every layer in both themes.

5

Narrow screens degrade gracefully

The 1120px container keeps 32px gutters; below ~640px, gutters drop to 16px and flex grids wrap. Never let content overflow — wrap or stack before clipping.

Icons

Icon system guidelines — sizes, stroke weights, and usage patterns.

Logic & Strategy

One drawing grid — or more. Simple icons draw on a 24×24 viewBox. Curves and several parts use 48×48 or 96×96 for double/triple resolution. The dine-in fork & spoon push further to 256×256 for precision line art — the grid is drawing resolution, not size: all these grids render at 14–32px. The artwork inherits the surrounding text colour via currentColor — stroke or fill, an icon never makes its own colour decision. The size shown is just the render size; the artwork never changes.

Outlines for simple, line art for detailed. Most UI icons are stroke-based — lighter next to text. A detailed glyph (like the fork) uses a higher grid and thicker stroke so fine lines (tines, curves) stay crisp at small render sizes. The same currentColor inheritance applies; pick one style per icon and never mix strokes and fills in the same glyph.

Placement strategy. A leading icon carries the verb (add, save, delete). A trailing icon signals navigation or disclosure (chevron, arrow, download-after). Never put two icons on one button unless the second is a badge. If an icon needs explaining, it's the wrong icon — not a missing tooltip.

Icon Sizes

14px — Small
16px — Default
18px — Large
24px — XL

Where each size lives: 14px — inline micro (badge icons, tiny captions, compact rows). 16px — default (buttons, list rows, toggles, table cells). 18px — large (toolbar icons, empty-state illustrations, alerts). 24px — XL (standalone, graphic headers, no nearby text). At 14px the stroke must be 2.5 or the icon becomes a smudge; at 24px, 1.5 is fine for a delicate look.

Stroke Weights

1.5 — Light
2 — Default
2.5 — Bold

Which stroke where: 1.5 — light, for 24px+ decorative icons (never below 18px). 2 — the default; use unless there's a reason not to. 2.5 — bold, for small sizes (14px), emphasis, and the "plus" icons on buttons. Never mix stroke weights within one view — mixed weights read as inconsistent system state.

Fallback & Accessibility

1

Icon-only is never unnamed

Every icon-only button carries an aria-label (see Buttons). The label is the meaning; the icon is the decoration — if the icon fails to render, the button still has a name.

2

Meaning never lives in the icon alone

Status icons pair with colour and text (Feedback Rules 05/06). An icon that only a sighted user can interpret is not confirmation.

3

currentColor only

Icons inherit colour via stroke="currentColor" — never hardcode a fill or stroke. Otherwise the icon breaks dark mode and disabled states.

4

Scale uniformly

Resize icons with equal width/height only. Non-uniform scaling distorts the 24×24 grid and makes strokes uneven — a squashed icon reads as broken UI.

5

Small sizes need heavy strokes

Below 16px, a 2.0 stroke blurs on low-DPI POS screens. Go 2.5 at 14px, or increase the size — don't let the icon degrade into a smudge.

Elements

How to wrap element groups using modern flex layouts, rem-based padding, and percentage-based widths.

Logic & Strategy

Why flex? Most UI is one-axis flow — a row of actions, a stack of settings, a row of order cards. Flex lays out along one axis and lets children size themselves, so rows of variable content (labels, prices, buttons) fit naturally. Grid is for true 2D layouts only — a fixed table of cards — and is rare in this system.

The mental model. The container decides direction (row / column), spacing (gap) and wrapping; the children decide their own size (flex, width). Don't let children fight the container — no margins on shared children, no width on the container's axis unless you mean it.

When each pattern: row — action groups, toolbars, label+value lines, order-card footers. column — settings stacks, form fields, card bodies. wrap — anything with an unknown count (tags, chips, payment buttons). Fixed equal count → flex: 1; exact proportions (60/40 split) → % widths — see the gap trap below.

Fallback & Accessibility

1

min-width: 0 on content children

A flex child with long or nowrap text refuses to shrink below its content width. Add min-width: 0 to any child that can hold a long label; pair with ellipsis where the label must truncate.

2

The % + gap trap

Equal % widths plus gaps overflow the container. Use flex-basis: calc(100% / N - gap × (N-1) / N) for exact columns, or flex: 1 when equal distribution is fine.

3

Wrap before clip

Unknown counts (tags, chips, options) get flex-wrap: wrap. A row that overflows its container is a layout bug, not a style choice.

4

border-box is assumed

The reset sets box-sizing: border-box everywhere — % widths include padding and borders. Don't fight it with content-box; the arithmetic breaks.

5

Truncate with a title

When a label must stay on one line (buttons, pills, table cells), use white-space: nowrap; overflow: hidden; text-overflow: ellipsis and keep the full text in the title attribute for hover + screen readers.

Components

Reusable UI patterns — cards, modals, tooltips, alerts, and badges built on the brand token system.

Logic & Strategy

Why components? They are the token system made visible — every component below is composed only from the Colour, Spacing, Radius and Shadow tokens, so the component layer holds zero design decisions. A token change re-themes every screen; a component change re-themes one pattern.

Elevation drives the stack. Each component sits at a specific elevation (see Spacing): cards rest on the page (--shadow-sm), modals float above it (--shadow-md + dimmed overlay), tooltips hover closest to the eye. If a component's elevation doesn't match its role, the hierarchy is wrong.

Choose by what the user must do: read → card. choose / confirm → modal. discover a hidden label → tooltip. be told something changed → alert. scan a status → badge. Two components with the same job means the pattern isn't decided yet.

Fallback & Accessibility

1

Modals trap focus and Escape

A modal is role="dialog" + aria-modal="true": focus moves inside, Tab stays inside (focus trap), Escape closes, and focus returns to the trigger. Without these, keyboard users are stranded behind the overlay.

2

Tooltips never hold critical info

If the content matters, it lives in the page — a tooltip is a convenience, not a source of truth. The trigger must be focusable (it is a button, not a span) so keyboard users get the tooltip too.

3

Alerts announce themselves

Dynamic alerts get role="alert" (or aria-live="polite") so screen readers announce the change without stealing focus. Static examples like these on the page are fine as-is.

4

Counts are never bare numbers

A count badge is meaningless alone to a screen reader. The accessible name reads the context: "3 new orders", not "3". Attach it to the label or use aria-label.

5

Cards are containers, not buttons

When a whole card is clickable, make the inner CTA the focusable element — never nest buttons inside a clickable card, and never make a div clickable without role + keyboard handling.

Motion & Feedback

Universal interaction rule: every action has a before, a feedback, and an after — so every action is confirmable by the visuals alone.

The Rule — Before · Feedback · After

Before

Resting state

The control shows what it is and what it does. The user hasn't touched it yet — nothing has happened.

Feedback

While pressing

Immediate tactile response — press, hover, focus. This happens in under 150ms, before the work is done.

After

Confirmation

The settled state that proves the action landed — checkmark, state change, or disabled. Never leave the user guessing.

Rule of thumb: if the user can't tell from the pixels alone whether their action worked, the feedback is missing.

The Rules

01

Confirm by visuals alone

Every action must be verifiable from the pixels — state, colour, icon, motion. If the user has to wonder whether it worked, the feedback is missing.

02

Feedback before work

Respond within 120ms (fast token). The heavy work may take seconds — the press response must never wait for it.

03

The after-state must differ from the before

A click that changes nothing is indistinguishable from a click that never registered. Flip the state: button → disabled + checkmark, tab → selected, toggle → slid.

04

Never animate instant flips

Theme, filters, selected tabs, counts — these are state flips, not transitions. Use 0ms (instant token). Animate only what moves in space.

05

Error is motion + colour + text

Shake + red border + caption. Never red alone (invisible to colour-blind users), never a caption alone (missed by fast eyes).

06

Success is a checkmark, not just green

Green alone can read as decoration. Pair it with the icon and a real state flip — disabled button, removed row, updated value.

07

Motion is communication, not decoration

Every animation answers a question: did it work? what changed? where did it go? If it communicates nothing, cut it. Never loop idle animation — spinners only while genuinely busy.

08

Least motion that confirms

Use the smallest duration and amplitude that reads clearly. When in doubt, a 120ms scale/translate micro-interaction beats a fancy 500ms entrance.

09

Respect reduced motion

Honor prefers-reduced-motion — swap motion feedback for instant state change. The after-state must still confirm.

If a rule conflicts with another, the after-state wins — confirmation beats polish, every time.

Fallback & Accessibility

1

Honor reduced motion for real

Rule 09 made concrete: @media (prefers-reduced-motion: reduce) collapses every duration to 0ms and skips entrance/spin/shake — but the after-state never disappears. The checkmark, the red border, the removed row all stay.

2

Old hardware is the baseline

POS terminals can be a decade old (an i3-2100 is the floor). Animations are transform/opacity only, never layout properties; long lists use content-visibility; no blur or heavy shadow animations. If it stutters there, it's too heavy everywhere.

3

Long work keeps the spinner

If an action runs past ~10s, keep the indeterminate spinner — never fake a progress bar. The contract is the after-state, not the elapsed time. Offer a cancel path for genuinely long operations.

4

Busy buttons must not double-fire

While feedback is in flight the control is disabled (see Buttons' rule 5). A second tap that restarts the cycle is the fastest way to break the before → feedback → after contract.

5

The state confirms, not the animation

When an animation ends, the after-state must persist — if the only thing left is the memory of motion, it was decoration (Rule 07), and the confirmation is missing.

Audit

Every interactive element carries a data-testid with an easy-to-understand name — the contract between the UI and automated tests.

The Convention

Tests (Playwright, Testing Library) select elements by data-testid — never by CSS class, DOM position, or visible text. Visible text gets translated; classes get refactored; the testid is the only stable handle.

data-testid=" feature - element [- action ]"
kebab-case, lowercase feature scope first describes what it is / does never position (no button-3) stable across locales unique per screen

One id per control, everywhere that control appears. If the same button exists in two features, prefix it with each feature — the id must be unique on the page.
