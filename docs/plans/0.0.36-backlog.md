## R36-01 ✅ — Analytics range silently shifts with the host timezone

**Closed.** The entry said this "needs a behaviour decision". It did not — the
decision was already made in the schema, and finding it beat inventing one:

```
crates/oz-core/migrations/20260813_init.sql:803      timezone TEXT NOT NULL DEFAULT 'UTC'
crates/oz-core/migrations/20260813_init.pg.sql:199   timezone TEXT NOT NULL DEFAULT 'UTC'
```

The column is `NOT NULL`, so a persisted store always has a zone; `null` reaching
`isoToday` means only "profile still loading" or "fetch failed". And the system's
own default for that column is `'UTC'`. So the fallback is `FALLBACK_STORE_TZ =
'UTC'` — deterministic, host-independent, and consistent with the backend rather
than a new product policy smuggled in as a bug fix. `storeOffsetMs()` parses only
fixed `±HH:MM` and returns 0 otherwise, so `'UTC'` lands on offset 0 the same way
the backend does.

Both host-local branches are gone: `isoToday` and `storeDateStr` now share one
code path, and `isoDay` — which existed only to read the device calendar — was
deleted. `isoToday` and `FALLBACK_STORE_TZ` moved to `analytics-data.ts` beside
`storeOffsetMs` and `rangeForGranularity`, which is where a pure date helper
belongs and which also removed a `react-refresh` lint warning that exporting
from the component file would have added.

**Verification, and why a normal test is not enough here.** Node fixes the
process zone at startup, so a single vitest run can never demonstrate
host-independence — the assertion that looks green on a UTC runner is precisely
the one that failed on a UTC+7 workstation. `scripts/check-tz-invariance.py`
therefore runs `src/__tests__/analyticsTimezoneAnchor.test.ts` under four zones
and requires identical results. Wired into `gates.json` as
`analytics-tz-invariance`, the `dev-ci.yml` `ui-test` job (whose runners are
always UTC, so this is the job's only non-UTC coverage), `scripts/check.sh`, and
the `pre-push` UI tier.

Two things confirmed rather than assumed:

  * **The invariance check is not vacuous.** Reintroducing the old host-local
    fallback made it fail, naming the two assertions that broke. It caught the
    bug via `America/Los_Angeles` only — the sensitivity is time-of-day
    dependent, so the script documents the arithmetic showing that
    `Los_Angeles` (differs while UTC < 17:00) and `Kiritimati` (differs once
    UTC ≥ 10:00) overlap to cover all 24 hours. Dropping either would leave a
    gate that passes at some hours and fails at others.
  * **The schema claim is checked, not trusted.** One test parses the migration
    and asserts its default equals `FALLBACK_STORE_TZ`, so the justification
    cannot silently rot. Verified non-vacuous by drifting the constant to
    `Asia/Jakarta` and watching it fail.

After the fix: 414 files / 7,788 passed / 0 failed, `tsc --noEmit` clean, eslint
0 errors, invariance green under all four zones.

**Found while fixing this — see `R36-05`.** `ui/src/features/reports/DashboardScreen.tsx`
has its own private `isoDay`/`today()`/`daysAgo` (L43–L68) with the identical
host-local defect, and no `storeTz` plumbing at all.

**Original analysis follows.**

**Where:** `ui/src/features/analytics/AnalyticsScreen.tsx:147-150`

```ts
function isoToday(storeTz?: string | null): string {
  if (!storeTz) return isoDay(new Date());          // ← host-local
  return new Date(Date.now() + storeOffsetMs(storeTz)).toISOString().slice(0, 10);
}
```

**Why it matters.** When a store has no timezone, "today" falls back to the
**machine's** zone. A POS is a fixed physical device in a fixed place, so the
correct anchor is the store's zone or an explicit configured default — never
whatever the OS happens to be set to. Two consequences:

- The same install opened on a UTC-configured server versus a UTC+7 workstation
  computes **different date ranges**, so "today's sales" and the daily/weekly
  boundaries disagree between surfaces that share a backend.
- `storeTz` is initialised to `null` (`AnalyticsScreen.tsx:362`) and loaded
  asynchronously, and the effect at `:380` returns early while it is null. So
  **every** first render uses the host-local anchor even for stores that *do*
  have a timezone configured; the correct value only applies after the load
  resolves and triggers a recompute.

**Evidence.** This is not theoretical — it is the mechanism that broke CI on
PR #95. `AnalyticsScreen.test.tsx:1346` failed deterministically on two
consecutive runs while passing locally. Measured with a temporary probe: the
low-stock fetch fires **2 times at `TZ=UTC` and 1 time locally**, because the
recomputed range differs between the two anchors. The test was made
independent of it in `cca9e5d0`, which fixes the *symptom only*.

**Proposed fix.**
1. Decide the fallback explicitly. Either require `storeTz` (and surface a
   configuration error when absent) or default to a documented constant rather
   than host time. Do not leave the choice to the OS.
2. Resolve the "null on first render" window: either gate the range computation
   until `storeTz` is known, or compute it once and pass it down, so the first
   paint cannot use a different anchor than the settled one.

**Verify.**
```bash
# both must produce identical ranges; today they do not
TZ=UTC    npx vitest run src/__tests__/AnalyticsScreen.test.tsx
TZ=Asia/Jakarta npx vitest run src/__tests__/AnalyticsScreen.test.tsx
```
Add a regression test that pins `isoToday(null)` behaviour, or deletes the
`!storeTz` branch entirely — a test that asserts the *absence* of host
dependence is the point.

## R36-02 ✅ — Tauri IPC test mocks miss their `_scoped` command names

**Closed.** Both halves of the proposed fix landed: the missing handlers were
added, and the reject-fallback now fails loudly via
`ui/src/__tests__/test-utils/invokeCoverage.ts`.

**The headline number was wrong here, in the understating direction.** This
entry said four files use the fallback; it is **five** —
`FeatureToggleScreen.test.tsx` was missed. And the real severity is not the
`_scoped`/plain ratio the table below guessed at. Instrumenting all five and
running them found:

| File | Actual gap |
|---|---|
| `SalesDashboardScreen` | 3 commands handled by plain name only, while `ui/src/api/reports.ts` invokes `_scoped` for **all 24** of its functions |
| `StaffManagementScreen` | **1** missing handler — `get_brand_settings` — which made **23 of its 26 tests pass while rendering the app shell's error branch** |
| `InventoryAdjustmentScreen` | none; already scoped correctly |
| `TaxConfigurationScreen` | none; already scoped correctly |
| `FeatureToggleScreen` | none — and its three plain names (`list_all_features`, `set_feature`, `set_features_bulk`) are *correctly* unscoped, sitting in the "genuinely global" allowlist category of `verify-scoped-coverage.sh` |

The `StaffManagementScreen` case is the one that justifies the whole exercise: a
single unmocked command, reached from the branding provider in the app shell
rather than the screen under test, silently degraded 23 assertions to
error-path checks that still went green. Nothing about that file's
`_scoped`-vs-plain ratio predicted it, which is why the ratio table below was
marked "suggestive, not conclusive".

The assertion was verified non-vacuous: renaming one `_scoped` handler in
`SalesDashboardScreen` made **3 tests fail** and named the command exactly.
After the fix, all five files pass (79 tests), the full UI suite is green
(413 files / 7,782 passed / 0 failed), and `tsc --noEmit` is clean.

Note the helper records the unmatched command but **still rejects**, so
components see precisely what they saw before — only the reporting changed, from
silent to failing. That keeps this from altering the behaviour under test.

**Original finding follows.**

**Where:** `ui/src/__tests__/SalesDashboardScreen.test.tsx:45-55` (and 3 sibling files)

The mock dispatches on command name and rejects anything unmatched:

```ts
if (cmd === 'get_category_breakdown') return Promise.resolve([]);
if (cmd === 'get_hourly_heatmap')     return Promise.resolve([]);
if (cmd === 'get_daily_revenue')      return Promise.resolve([]);
return Promise.reject(new Error(`Unknown command: ${cmd}`));
```

But production calls the **scoped** names — `ui/src/api/reports.ts:169` invokes
`get_daily_revenue_scoped`, and `api-reports-contract.test.ts` /
`reports-ipc-contract.test.ts` both assert the `_scoped` spelling. So these
three calls **always reject**; the test survives only because the component
swallows the rejection and the assertion happens to land in a window where that
is harmless.

**Why it matters.** This is a latent mock gap masquerading as a timing flake.
`SalesDashboardScreen > shows KPI cards` failed once on a full parallel run and
passed in isolation (6/6 twice) — which is exactly how a swallowed rejection
looks when load changes the ordering. Two dangers:

- The test is **not actually testing the data path**. It asserts KPI cards
  render while every revenue IPC call is failing.
- Any real regression in those handlers stays invisible, because the mock was
  never exercising them.

**Scope of the audit.** Four test files use this `Unknown command` reject
fallback, with uneven scoped coverage:

| File | `_scoped` handlers | plain `cmd ===` checks |
|---|---|---|
| `SalesDashboardScreen.test.tsx` | 4 | 11 |
| `InventoryAdjustmentScreen.test.tsx` | 2 | 2 |
| `StaffManagementScreen.test.tsx` | 26 | 18 |
| `TaxConfigurationScreen.test.tsx` | 35 | 39 |

The counts are suggestive, not conclusive — the ratio is not itself the defect.
What matters is whether every command the component under test actually invokes
has a handler.

**Proposed fix.**
1. For each of the four files, enumerate the commands the component really
   calls and add the missing `_scoped` handlers.
2. Better: make the reject-fallback **fail the test loudly** instead of
   returning a rejected promise the component may swallow — e.g. record
   unmatched commands and assert the set is empty in `afterEach`. That converts
   this whole class of silent gap into a visible failure.

**Verify.**
```bash
cd ui
npx vitest run src/__tests__/SalesDashboardScreen.test.tsx   # must pass
npx vitest run --reporter=verbose src/__tests__/SalesDashboardScreen.test.tsx
# and confirm no "Unknown command" appears anywhere in the output
```

**Related, deliberately not done here — `retry`.** `ui/vite.config.ts` sets no
`retry`, so any race fails the job outright. Adding `retry: 2` would have
greened PR #95 immediately. It is **not** recommended as the fix for this item:
retry masks a swallowed rejection rather than closing it, and it would also hide
genuinely new failures. Consider `retry` only as a separate, explicit policy
decision once R36-02 is closed.

## R36-03 ✅ — orphaned website assets (resolved; the original write-up understated it)

**Resolved in this release** by deleting 7 unreferenced SVGs — 1,025,475 bytes.
The guard in §"The guard" below is now implemented too, closing the entry.

### What this entry originally got wrong

As written, this entry was scoped to the `footer-*` family and reported one
381 KB offender. Sweeping the whole directory properly, the largest file was not
`footer-instagram.svg` at all — it was **`logo-indonesia-map.svg` at 639,106
bytes**, which this document never mentioned. Anchoring on a filename prefix
instead of the directory is the same mistake class the Fluent page audit hit:
auditing the obvious family and missing the outlier.

### Actual inventory at `cca9e5d0`

`website/src/assets/` held 15 files. Exactly 8 are imported, all by literal
`import x from '../assets/y.svg?url'` — there is no `import.meta.glob` and no
template-string asset path anywhere in `website/src`, which is what makes a
zero-reference grep trustworthy here rather than merely reassuring.

| Orphan | Bytes |
|---|---:|
| `logo-indonesia-map.svg` | **639,106** |
| `footer-instagram.svg` | **381,629** |
| `footer-discord.svg` | 1,585 |
| `logo-os-apple-white.svg` | 1,139 |
| `footer-telegram.svg` | 1,030 |
| `footer-facebook.svg` | 628 |
| `footer-x.svg` | 358 |
| **total** | **1,025,475** |

`footer-instagram.svg` is not a vector at all: an `<svg>` wrapper around **six
base64-encoded `<image>` rasters**. `PlatformIcon.astro` imports
windows/android explicitly, so `logo-os-apple-white.svg` is genuinely unused
rather than resolved dynamically. `Footer.astro` renders all five social icons as
**inline `<svg>`** (L22/33/44), so the whole `footer-*` asset family was dead on
arrival.

### Why it mattered

A 381 KB icon wired into the footer would have landed on every page and undone
the Lighthouse work from the same release (`ebfa2227` self-hosted fonts,
`3b505842` deferred CSS, `4afa18c0` flattened island waterfall). Deleting is
also the only remaining option that costs nothing: the blobs are already in
history, so the repo size is fixed either way — but the working tree and every
future checkout get lighter.

### The guard — now implemented

`scripts/verify-website-assets.py` enforces all three suggestions, registered in
`gates.json` as `website-assets` (status `required`) and wired into the live
`dev-ci.yml` `website` job, `scripts/check.sh`, and the `pre-push` website tier.
In CI it runs *before* `npm ci` — it is stdlib-only, so an oversized asset fails
in ~1s rather than after a minute of dependency setup.

The third check needed the care this entry warned about, and the implementation
handles it structurally rather than by trust: the orphan check first scans
`website/src` for `import.meta.glob`, template-string asset paths, `+`
concatenation and `.concat(…assets`, and **disables itself with a note** if any
exist. A zero filename grep only means "unused" while resolution is provably
static, so the guard retires the moment that premise stops holding.

One honest compromise: `logo-os-android.svg` is a brand export embedding 14
base64 rasters — the same shape as the deleted `footer-instagram.svg`. At 52 KB
it is under budget and predates the check, so it is grandfathered in a named
`KNOWN_RASTER_SVGS` set documented as a ratchet baseline that should only ever
shrink, not as an endorsement. Without that the guard would have shipped red.

Verified with 5 negative tests run against temp copies of the tree, never the
real one: baseline passes, oversize fails, new base64 svg fails, orphan fails,
and orphan-plus-glob correctly stands the orphan check down. Two regex bugs were
found that way — the first version reported all 8 legitimate assets as orphans
because it captured Vite's `?url` suffix as part of the filename.

**Verify.**
```bash
ls website/src/assets                     # 8 files, all imported
git grep -n "from '.*assets/" -- website/src | wc -l   # 8 literal imports
```

## R36-04 ✅ — Nothing enforces the conventional-commit rule

**Closed.** `.githooks/commit-msg` now validates the subject, and `style` was
added to the documented type list so the gate and practice agree. The four
malformed commits below are left in history as instructed — they are pushed and
referenced by PR #95.

What the gate accepts beyond the strict format: git-generated subjects
(`Merge …`, `Revert …`, `fixup!`, `squash!`) and an empty subject, so normal git
workflows are not broken. Verified with 30 cases (16 accept, 4 git-generated
accept, 10 reject including the exact four shapes below), and confirmed to
actually block a real `git commit`.

**Not done:** the CI-side check suggested at the end of this entry. The hook is
opt-in, so a clone that skips setup is still ungated — closing that needs a new
`dev-ci.yml` job, which is a separate decision.

**Original finding follows.**

**Where:** `.githooks/` contains `pre-commit`, `post-commit`, `pre-push` —
**there is no `commit-msg` hook.**

**Why it matters.** `AGENTS.md` states the format is "enforced" and lists the
allowed types, but enforcement is prose only. Four commits on the 0.0.35 branch
demonstrate the gap — each is pasted `git status --porcelain` output used as the
message:

| Commit | Subject |
|---|---|
| `2eea3d07` | `deleted:    lighthouse-report.json` |
| `faa5dae0` | `modified:   .gitignore` |
| `5855c429` | `updated gitignore` |
| `84a71f3e` | `new file:   lighthouse-report.json   new file:   website/src/assets/footer-discord.svg …` |

`84a71f3e` and `2eea3d07` are the same file added then deleted, so the churn is
invisible in the final tree but permanent in history. These are the commits a
release-notes generator or `git log` reader sees first when scanning the tail of
the branch.

**The documented rule also disagrees with practice.** `AGENTS.md:162-170`
enumerates the allowed types as `feat`, `fix`, `docs`, `chore`, `test`,
`refactor`, `perf`, `ci`, `audit` — **`style` is not on that list**, yet 8
commits on the 0.0.35 branch use it (`130c7556`, `e0f2ca9b`, `04465711`,
`2d517b55`, `7dde51c2`, `cfd0f183`, `c3b7c72b`, and `ad9c60e9` with no scope),
several of them written during this very work. So a strict gate built from the
current table would reject commits the repo already treats as normal. Resolve
this first: either add `style` to `AGENTS.md` or migrate those commits'
successors onto an allowed type. The regex below assumes `style` is accepted,
because that matches what the repository actually does.

**Do not rewrite history.** All four are already pushed to `origin/0.0.35` and
referenced by PR #95. Rebasing to fix subjects would break the PR's review
state and anyone else tracking the branch. Treat the four as permanent and fix
the *gate*.

**Proposed fix.** Add `.githooks/commit-msg` validating the subject against
`^(feat|fix|docs|chore|test|refactor|perf|ci|audit|style)(\([^)]+\))?!?: .+`
— the exact type list `AGENTS.md` enumerates — and reject anything else with a
message pointing at that table. Keep it subject-only; bodies are free-form.

Note the same caveat that applies to every other hook here: `core.hooksPath` is
set by `scripts/setup-dev.ps1` and is **not versioned**, so a fresh clone that
skips setup gets no local gate. If this one matters, it needs a CI-side check
too — e.g. validating commit subjects in `origin/main..HEAD` on pull_request.

**Verify.**
```bash
git log --format='%s' origin/main..HEAD \
  | grep -vE '^(feat|fix|docs|chore|test|refactor|perf|ci|audit|style)(\([^)]+\))?!?: '
# expect: empty
```

## R36-05 ✅ — `DashboardScreen` has the same host-local anchor R36-01 just fixed

**Closed.** `DashboardScreen` now fetches the primary store and anchors its
default 30-day range to the store's zone, using the same helpers as
`AnalyticsScreen`.

`isoDaysAgo(daysAgo, storeTz)` was promoted into `analytics-data.ts` from what
had been a private closure inside `AnalyticsScreen` (itself a copy of the same
arithmetic), so the two screens now share one implementation and cannot drift
apart on the REP-03 rule. `AnalyticsScreen`'s local `storeDateStr` is gone.

Only `today()` and `daysAgo()` were actually defective. `isoDay`,
`parseLocalDate`, `shiftDate` and `daysBetween` stay: they do calendar
arithmetic on already-formatted `YYYY-MM-DD` strings, where the local `Date` is
just a scratch container and the result is zone-independent. Replacing those
would have been churn dressed up as a fix.

The re-seed guard matters: `rangeTouched` is set by both date inputs, so a slow
IPC response cannot overwrite a range the operator already edited. That is
covered by its own test.

**The test that proves it, and why the mock was the trap.** `DashboardScreen.test.tsx`
mocks `@/api/reports` at module level and has **no** `@tauri-apps/api/core` mock,
so the new `getPrimaryStoreScoped` call initially hit real `invoke`, rejected, and
was swallowed by the `.catch` — the component fell back to UTC and all 23 tests
still passed. A green suite here meant nothing until `@/api/stores` was mocked
too. This is the same failure shape as R36-02: an unmocked call that rejects
silently.

The anchoring test computes its expected dates with explicit UTC arithmetic
rather than calling `isoToday`/`isoDaysAgo`, so it does not assert the helper
against itself. `scripts/check-tz-invariance.py` now runs both the pure anchor
test and this component test under four host zones (31 tests), which is the only
way to prove the whole fetch → state → re-seed → render chain is
host-independent rather than just the helper.

Verified non-vacuous: restoring the old host-local initial values and neutering
the re-seed made the invariance check fail under `America/Los_Angeles`, naming
"anchors the default range to the primary store timezone (R36-05)".

After the fix: 414 files / 7,790 passed / 0 failed, `tsc --noEmit` clean,
invariance green under all four zones.

**Original analysis follows.**

**Found while fixing `R36-01`, and it is the same defect with less mitigation.**

`ui/src/features/reports/DashboardScreen.tsx` carries its own private date
helpers, all anchored to the device calendar:

| Line | Function | Problem |
|---|---|---|
| L43–47 | `isoDay(d)` | reads `getFullYear`/`getMonth`/`getDate` — host zone |
| L48 | `today()` | `isoDay(new Date())` |
| L49 | `daysAgo(n)` | `d.setDate(...)` on a host-local `Date` |
| L52–55 | `parseLocalDate(s)` | deliberately builds a local-midnight `Date` |
| L65–69 | `shiftDate(s, days)` | round-trips through the two above |

Those feed store-scoped queries directly — L181 `getDailyRevenue(from, to,
sessionToken)`, L182 `getTopProducts(...)`, L186 the previous-period comparison —
and `ui/src/api/reports.ts` invokes the `_scoped` variant for every one of them.
So the window boundaries come from the host while the data comes from the store.
The file contains **zero** mentions of `storeTz`, `timezone`, or
`getPrimaryStore`, i.e. none of the REP-03 plumbing AnalyticsScreen has.

**Severity: this is a LIVE, user-facing bug. An earlier revision of this entry
said the opposite, and was wrong.**

It claimed `DashboardScreen` was "not routed — only its own test imports it", and
on that basis offered deleting it as the likely-correct option. That conclusion
came from a truncated grep: the command piped through `Select-Object -First 6`,
and because `ui/src/__tests__/` sorts before `ui/src/features/`, all six lines it
showed were test files. The real answer was the seventh line and beyond.

The screen is reachable three ways:

## R36-06 ✅ — Three more routed reports screens are store-zone-blind

**Closed.** All three now fetch the primary store and anchor their default
window via the shared `isoToday()` / `isoDaysAgo()` helpers, with a
`rangeTouched` guard. `monthAgo()` was deleted rather than patched, which also
removes its DST sensitivity.

**This entry is where the test-quality work got interesting, and it caught me
out.** The first version of the anchoring tests hardcoded `timezone: '+14:00'`
and asserted the inputs showed the +14-shifted date. The sabotage test — neuter
the re-seed, expect the gate to fail — came back saying the tests **still
passed**. Cause: `+14:00` shares a calendar date with UTC whenever the UTC hour
is below 10, so for roughly ten hours of every day the assertion compared the
store date against itself. That is precisely the "passes at some hours, fails at
others" property the `check-tz-invariance.py` header warns about, and I had
walked straight into it one commit later.

Fixed structurally in `ui/src/__tests__/test-utils/storeZoneCase.ts`:
`discriminatingStoreZone()` picks `+14:00` or `-10:00` based on the current UTC
hour. Those two windows are complements — `+14` differs from UTC when hour ≥ 10,
`-10` differs when hour < 10 — so one of them always discriminates.
`assertCaseDiscriminates()` then fails the test loudly if it ever doesn't, so
the property is enforced rather than assumed. After the change the sabotage
fails in **all four zones**, not just one.

Second flaw the same sabotage exposed: resolving the store eagerly **races**.
The re-seed changes `startDate`, the fetch effect depends on it and refires, and
`loading` unmounts the date inputs mid-assertion — `waitFor` found the input,
then the very next line couldn't. The "does not clobber" tests now hold the
store response in a deferred promise, so the edit provably happens before the
profile arrives. That is both deterministic and a more faithful model of the
real slow-IPC case.

Verified: sabotage of all three screens' re-seed → gate fails in 4/4 zones;
R36-05's own sabotage still fails; clean run 140 tests identical across 4 zones;
full suite 414 files / 7,796 passed / 0 failed; `tsc --noEmit` clean.

**Original analysis follows.**

Found by sweeping for the R36-01/R36-05 class after fixing it twice. **These are
not the same defect**, and the difference matters for priority:

| Screen | Route | Helper | Anchor |
|---|---|---|---|
| `SalesReportScreen` | `reports` (`register.tsx:23`) | `today()` L89-91, `monthAgo()` L93-97 | **UTC** |
| `CustomReportScreen` | `custom-report` (`register.tsx:57`) | `today()` L45-47 | **UTC** |
| `MenuEngineeringScreen` | `menu-engineering` (`register.tsx:45`) | `today()` L93-95 | **UTC** |

`today()` here is `new Date().toISOString().slice(0, 10)` — `toISOString()` is
UTC, so unlike `DashboardScreen`'s `isoDay(new Date())` these are **already
host-independent**. They will not flake between a UTC CI runner and a UTC+7
workstation, which is why they rank below R36-01/R36-05.

The real defect is that they ignore the store's zone entirely — all three have
zero references to `storeTz`, `timezone`, or `getPrimaryStore` — while querying
store-scoped data. Concretely: a `+07:00` store at **06:00 local** is `23:00 UTC`
the previous day, so "today" on these screens shows **yesterday's** date for the
first seven hours of every Indonesian business day. That is the morning window,
which for a POS is when a owner actually looks at a report.

**One genuine mixed-zone bug**, separate from the anchor question:
`SalesReportScreen.monthAgo()` (L93-97) mutates with host-local `d.getDate()` and
then reads back with UTC `toISOString()`:

```ts
const d = new Date();
d.setDate(d.getDate() - 30);           // host-local day-of-month
return d.toISOString().slice(0, 10);   // UTC calendar
```

The two halves use different calendars. How often that actually shows was
measured rather than guessed — replaying a year of hourly instants through the
real expressions under each host zone, counting cases where the window came out
something other than exactly 30 days:

| Host zone | off-by-≠30 | of | detail |
|---|---|---|---|
| `UTC` | 0 | 8760 | — |
| `Asia/Jakarta` (+7) | 0 | 8760 | — |
| `Pacific/Kiritimati` (+14) | 0 | 8760 | — |
| `America/Los_Angeles` | **60** | 8760 | 30h → 29 days, 30h → 31 |
| `Europe/London` | **60** | 8760 | same |
| `Australia/Sydney` | **60** | 8760 | same |

So it is a **DST-only** defect, ~0.7% of hours, and it never fires in a zone
without DST transitions. Since this is an Indonesian POS and Indonesia has no
DST, it is effectively unreachable in the target market — which is why this entry
is 🟠 and not 🔴. It would bite a deployment in a DST region, and the fix is free
once the anchor work is done anyway.

**Fix.** All three should use `isoToday(storeTz)` / `isoDaysAgo(n, storeTz)` from
`features/analytics/analytics-data.ts`, which R36-05 made shared for exactly this
reason, plus the same fetch-and-re-seed pattern with a `rangeTouched` guard.
`monthAgo()` should be replaced outright rather than patched — `isoDaysAgo(30,
storeTz)` is both zone-correct and window-exact, and removes the DST sensitivity
as a side effect.

**Do not skip the mock.** R36-05's lesson applies directly: these screens' tests
mock `@/api/reports` at module level, so a new `getPrimaryStoreScoped` call hits
real `invoke`, rejects, and is swallowed — the store-zone path stays untested and
the suite stays green. Mock `@/api/stores` in the same change.

## ✅ CLOSED — the redness was the scanner's bug, and it had a nastier half

Both fixes landed, in the order planned: `48aa000f` (scanner) then `8033a3e3`
(triage). `scan-unwrap-panic.py --fail-on-recoverable` now exits 0 with **130

for single-line blocks. For the multi-line audit stamp, just its first line was
recognised as a comment and lines 2..n-1 were scanned as code. That produced:

- **6 false positives** — all at line 4 of a file whose stamp says it is clean.
  A file failed the cleanliness gate because of the sentence documenting that it
  passes. 9 production files carry `unwrap()`/`expect()` in stamp prose.
- **1 suppressed real finding** — unstripped stamp prose also feeds the

  `cfg(test)` skip and **stopped checking the rest of that file entirely**. A

  scanner exits 0, new scanner reports.

So the rule an agent would have learned from the broken tool is exactly inverted:
*writing about your tests in a stamp disables the audit of your production code.*

**A second bug surfaced while fixing this: the gate fought `cargo fmt`.** The
invariant marker had to sit on the same or immediately-preceding *line*, so a
multi-line comment block or a fmt-wrapped builder chain counted as undocumented.

the block. Verified across six placements: trailing / adjacent / above-a-chain

each case reported exactly 1 finding, so none "passed" because the scanner failed
to read the file. The commit that followed proved it for real: the pre-commit hook
ran `cargo fmt`, rewrapped the code, and the gate stayed green.

## R36-15 🔴 — The pre-commit hook was corrupting binary files it claimed never to touch

**Closed in 0.0.36.** Found while chasing a phantom `M scripts/start-desktop.bat`
that `git diff --numstat` reported as a zero-content change.

### The bug

`.githooks/pre-commit` step 2 documented itself as: *"never touches binaries or
staged deletions."* It touched binaries. Two independent ways:

**1. `text=auto` is not a binary filter.** The step asked
`git check-attr text -- "$f"` and skipped anything that wasn't `set`/`auto`. But
`.gitattributes` says `* text=auto`, so **every** path answers `auto` — the "auto"
part is git's own content sniffing, which happens later, inside `git add`. The
filter therefore let PNGs through, and then:

```
tr -d '\r' < icon.png | cmp -s - icon.png     # differs: PNGs contain CR bytes
```

so it rewrote the file and `git add`ed the result. A PNG's signature is
`89 50 4E 47 0D 0A 1A 0A` — the `0D 0A` is *required by the spec* as a
line-ending sanity check. Deleting the CR invalidates the image.

Measured on `apps/desktop-client/icons/32x32.png` using the hook's own logic:

```
before: 1515 bytes, sha 1f52ac23df231e14
after : 1507 bytes, sha 581b557e960df4cd
PNG SIGNATURE DESTROYED
```

**40+ tracked binary files contain CR bytes** and would be rewritten on any commit
that stages them. Icons, fonts, and anything else binary added later.

**2. It ignored per-path `eol` overrides.** `check-attr text` was consulted;
`check-attr eol` was not. `.gitattributes` pins `*.bat text eol=crlf` with the
comment *"cmd.exe mis-parses labels/goto in LF-only batch files"*. The hook saw a
`.bat` as text and stripped its CRs.

The index storing LF is correct and intended (`.gitattributes` says so explicitly).
What broke is the **working tree**, which is supposed to be CRLF — producing both a
genuinely LF batch file on disk and the phantom-dirty `git status` that started the
hunt.

### The natural experiment that confirmed it

Ten tracked `.bat` files. Exactly one — `scripts/start-desktop.bat` — had been
committed through this hook during this session:

| file | index CRLF | worktree CRLF | |
|---|---|---|---|
| `scripts/start-desktop.bat` | 0 | **0** | ← through the hook |
| `scripts/start-local-sync.bat` | 0 | 167 | |
| `scripts/run-hfuzz-overnight.bat` | 0 | 116 | |
| … 7 more | 0 | matches line count | |

Every file that never passed through step 2 kept its CRLFs. The one that did lost
all 90.

### Fix

`.githooks/pre-commit` now applies three exclusions before rewriting anything:
`check-attr text`, then `grep -qI ''` (NUL-based binary detection, independent of
git's attribute layer), then `check-attr eol` skipping `crlf`. Working-tree CRLFs
were restored in `start-desktop.bat`, and the phantom `M` disappeared.

`scripts/test-eol-guard.sh` (gate `eol-guard`, `required`, in `check.sh`) **extracts
the live guard from the hook by line range and runs it**, rather than copying it —
a copied fixture keeps passing after someone edits the hook, which is the failure
mode this whole release has been cleaning up. It also fails loudly if either guard
vanishes. 9/9 cases: `.bat`/`.cmd` skipped, real PNG skipped, markdown/json/txt
still normalized, plus an end-to-end pass proving the PNG's bytes and the batch
file's CR count survive.

Three bugs surfaced while writing that test, all worth keeping in mind:

- **Greedy extraction.** Counting `case`/`esac` depth from the first `case` stopped
  at the first `esac`, capturing half the guard. The result: `.bat` reported `NORM`
  and looked like a broken *fix*, when the test simply wasn't reading the eol
  block. Now anchored on the eol case and asserting the extracted length.
- **`sed 's/continue$/…/'` only matched the end-of-line form.** The hook has
  `continue ;;`, bare `continue`, and `continue # comment`. The unmatched ones
  printed a shell error and fell through to `NORM` — again indistinguishable from a
  real failure. Fixed by running the guard inside a one-iteration loop so
  `continue` means what it means in the hook.
- **A synthetic `\x89PNG\r\n\x1a\n` header is not detected as binary**, because
  grep's heuristic is NUL-based and that signature has no NUL. The fixture had to
  use the real icon.

### Not done

No binary file in `HEAD` is currently corrupt — the hook only rewrites *staged*
files, and none of the 40 had been staged since step 2 landed. Verified by
comparing each tracked icon's working-tree hash to its blob. So this was a landmine
disarmed before it went off, not a recovery.

**Verify.**
```bash

#   expect: 89 50 4e 47 0d 0a 1a 0a
```

## R36-20 — 42 dead keys across 7 mock factories, and one file that mocks the wrong name

**Opened by the audit that followed `0c60af50`; now gated by `31db539f`.**

### The two directions a mock can drift, and why only one is loud

| direction | what happens | detected? |
|---|---|---|
| **missing** export | code calls something the mock lacks → vitest prints `No "X" export is defined on the "…" mock` | yes, if anyone reads the log — and a caller with a `.catch` still goes green |
| **dead** key | mock defines something the module no longer exports → **completely silent** | was no; now gated |

A dead key matters because of what a test then does with it: it arranges a response on a
name nothing can call, so the arrangement configures nothing, and the component reads a
*different*, live function and receives the factory's default. The test asserts on data it
believes it supplied.

### The concrete case

`ShiftManagementScreen.test.tsx` mocks `@/api/shifts` with 7 keys. Verified against source:

  * the screen imports 6 functions, of which **`createCashPayoutScoped` is not mocked** —
    a payout in a test would throw;
  * the mock defines **`createCashPayout`** and **`getShiftReport`**, neither of which
    `@/api/shifts` exports at all;
  * `mockCreateCashPayout` is declared (L22) and wired to the **dead** name (L32), so that
    arrangement is a no-op today.

Nothing fails only because no test in the file triggers a payout. That is the whole
problem with the silent direction: the file looks like it covers cash payouts.

### Scope

42 dead keys across 7 factories — `createShiftsApiMock` (7), `createSalesApiMock` (13),
`createSettingsApiMock` (10), `createProductsApiMock` (3), `createHardwareApiMock` (3),
`createRetailProductsApiMock` (4), `createRetailCurrencyApiMock` (2). Almost all are legacy
unscoped names left by the ADR #7 scoped migration. **Two are not legacy:**
`finalizeSaleScoped` and `voidPendingSaleScoped` are *Scoped* names the sales module does
not export either — a typo or a removed command, and worth identifying before anyone
writes a test against them.

### Why the gate freezes a baseline instead of fixing the debt

The keys are unreachable by definition, so deleting them repairs nothing — and
`mocks/api.ts` is imported by most of the UI suite while several agents commit to this
branch concurrently. So `mockFactorySurface.test.ts` requires the dead set to equal a
frozen map **exactly**: adding a dead key fails, and *removing* one also fails with a
message to shrink the map. A plain allowlist would let the baseline rot after the
cleanup that shrinks it; equality makes every reduction a tracked edit.

Proven to have teeth by sabotage in three directions — add dead → FAILS, remove dead →
FAILS, add a key the module really exports → PASSES (correct work is not punished), with
`api.ts` restored byte-identical each time.

### How the population scan was built, and why it stayed a throwaway

Three revisions, each wrong in a different direction:

| revision | criterion | failure |
|---|---|---|
| 1 | `token ?` … `Scoped(` within 160 non-`;` chars | spanned statements → **4 false positives** on `SettingsPage` |

`(id: string) => …` — that the codebase uses most. **When a scan's count goes DOWN after
tightening it, ask what the tighter rule now fails to see**, not only what it excludes.

The scan is not a gate and should not become one without handling multi-line ternaries. Its
value was the population number, which the earlier 9%-coverage import scan could not give.

59. **The intermittent UI flake, root-caused — and my first diagnosis was wrong.**
    `KdsEnrollmentModalPure.test.ts` failed once in ~5 full runs, passed in isolation. The
    original entry here blamed the suite-wide mock-leak debt, reasoning that `pool: 'threads'`
    plus `fileParallelism: true` makes file order non-deterministic. **That was wrong, and the
    wrongness is instructive:** "fails in the full suite, passes alone" reads as ordering but is
    equally consistent with *load*, and the load explanation was the true one.

    **Actual cause: a wall-clock race.** The test read the clock twice —
    `new Date(Date.now() + 90_000)` to build the token, then `Date.now()` as the argument — and
    `secondsUntilExpiry` is `Math.max(0, Math.floor((expiresAt - now) / 1000))`. So the result is
    `floor(90 - δ/1000)` where δ is the scheduling gap between two adjacent statements. δ = 0
    gives 90; **δ = 1ms gives 89**. The assertion held only while both reads landed in the same
    millisecond, which is near-certain on an idle machine running one file and merely likely when
    492 files are competing for threads. Proven with absolute instants, which cannot drift:
    gap 0 → 90, gap 1 → 89, gap 999 → 89.

    Two more instances of the same bug in the same file: the "default-now" case captured `now`
    locally but the function reads `Date.now()` *itself*, so the comment claiming the instant was
    pinned described something that was not happening at all; and the sub-second case computed
    `future` and `now` from two separate reads, leaving a 500ms margin instead of an exact one.

    **Fixed** by reading the clock once and deriving both values from it, using fake timers for
    the default-now path (the only way to pin a clock the callee reads), and absolute instants for
    the boundary cases.

    **The lesson is more valuable than the fix: a race cannot be caught by a mutation test that
    runs it once.** Reintroducing the double `Date.now()` passed 6/6 in isolation, because the
    mutant only fails under load. Standard Red/Green discipline here silently reports "the guard
    works" when the guard documents a mechanism it cannot detect.

    **The gate I proposed in the same breath does not work, and measuring it is what showed that.**
    The suggestion was a static check for any `it()` block reading `Date.now()` twice. Scanned:
    **12 such blocks across 4 files, of which 9 are provably safe** — `useShiftTimer` asserts
    `toBeLessThanOrEqual(Date.now())`, where a later read only helps; one case clamps to 0 so no gap
    can change it; the rest use minute- or hour-scale offsets where 1ms is irrelevant. **That is a
    75% false-positive rate**, so the check as sketched would be noise, and it is recorded as
    rejected rather than deferred. The actual discriminator is narrower and harder to see
    statically: exact equality against a value derived from two clock reads at *second* granularity.

    **Someone has met this class before and handled it by convention, not by gate** —
    `SyncSection.test.tsx:397`: *"Buffer of +1h guards against ms drift: the component's Date.now()
    runs"*. That comment is the closest thing the repo has to a defence, and it is a manual margin
    applied by whoever noticed, which is why the three fragile cases survived to this round.

    Same underlying issue as item 58's date bomb, at a different granularity: that one drifted by
    whole days and failed for everyone every day; this one drifts by milliseconds and fails under
    load. Both are time-dependent test data, and neither is gated. Very probably also the failure
    round 48 could not identify.

    asserts that the same pipeline **succeeds without it** (exit 0), demonstrating the masking this
    gate exists to prevent. If that control ever stops holding, the guard is protecting nothing and
    the message says so. Proven live: without pipefail `false | tee` → **0**, with → **1**.

    `resolveBash()` walks up from `git --exec-path` and **rejects anything under `System32`/`SysWOW64`**,

### The meta-lesson: a static analysis gate needs a liveness case

Five separate plumbing bugs in the extractor built this round, and **every one of them
reported a clean zero instead of an error**:

| # | bug | symptom |
|---|---|---|
| 1 | non-greedy regex stopping at the first nested brace | 0 findings against a defect seen in test output |
| 2 | body slice landing on an `overrides = {}` default | 8 well-populated factories reported 0% |
| 3 | indentation assumed from a printout's own prefix | every factory reported 0 keys |
| 4 | backticks in a `//` comment → parser in string mode | dropped the last key; broke it on the comment explaining the fix |
| 5 | doubled path segment (`src/api` + `api/products.ts`) | **0 broken across all 417 files** |
| 6 | subject regex matched only default imports; every card test uses named | `subjects=0`, all 414 files skipped |
| 7 | providers counted as subjects (`ToastProvider` is in all of them) | `subjects=2`, "exactly one" rule skipped every file |
| 8 | searched whole text, so `sessionToken:` **inside the mock** counted as "prop passed" | the detector fell for the exact camouflage it was built to find |
| 9 | baseline walked back to the first revision with the mock, which already had my fix | self-validation failed on a **correct** criterion and a wrong expectation |

Bugs 4 and 5 were only caught because `mockSurfaceStatic.test.ts` asserts that it finds
what it must. **A static analysis gate with no liveness case is indistinguishable from a
gate that passes**, so a green result from it is not evidence. Any future source-scanning
check should carry at least one assertion that a known-present thing was found.

**⚠️ And a liveness case is not sufficient — print the denominator too.** The scan built
from bugs 6–9 eventually passed self-validation and reported `SAME-SHAPE FINDINGS: 0`
across 414 files. That zero was *true but empty*: the funnel's final stage had **0 files
in it**, because after `0baf1898` fixed the one member, no remaining file both mocked
`WorkspaceContext` and rendered a prop-taking card. "The class is empty" and "the scan
looked at nothing" produce the same output, and only the per-stage counts tell them
apart. The follow-up that actually found something (`65971d0f`) came from abandoning the
combination filter and asking the simpler population question directly: *how many
components take a `sessionToken` prop, and does each of their tests supply one?* — eight
components, one gap.
